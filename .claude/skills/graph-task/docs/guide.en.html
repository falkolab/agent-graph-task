01 / Architecture

Responsibilities and boundaries

The skill defines how work proceeds. The protocol defines mandatory quality rules. The execution mechanism is chosen for the task. Advisor is not part of the skill.

ENTRY POINT

Skill /graph-task

Receives the request, binds the contract, creates the graph, and follows the verification stages. Loaded only when invoked explicitly.

RULES

protocol.md

Detailed rules for baseline measurements, permissions, artifact versions, gates, reviews, limits, budgets, stopping, and resumption.

EXECUTION

Tools / Workflow

Direct tool calls, bounded subagents, or native Dynamic Workflows. Not automatic fan-out for every task.

02 / Execution options

One approved graph, two execution modes

These are not competing systems. graph.md specifies what needs to be done and how to verify it. Claude chooses how to execute the plan. With Dynamic Workflow, the same plan gains a second, executable representation in JavaScript.

From specification to execution and verified artifacts

MODE A

Without Dynamic Workflow

Claude executes nodes directly or delegates bounded research and reviews to subagents. The same graph.md, permission boundaries, evidence, gates, and closure artifacts still apply.

Best for small or heterogeneous graphs where a separate JavaScript orchestrator would add overhead.

MODE B

With Dynamic Workflow

Claude writes the JavaScript execution graph. The script defines dependencies and call order; the runtime executes agents and retains intermediate results. graph.md remains the approved specification, not a second live scheduler.

Best for many similar independent tasks when scripted orchestration reduces pressure on the main context.

Synchronization and ownership: each Workflow is bound to one revision/hash of graph.md and a limited node subset. Before launch, record the phase, graph hash and authorization in progress.md; the saved workflow.js path and hash are recorded there too, and the script is launched via scriptPath; the root adds the actual run ID after control returns, if available. Gate agents verify saved outputs inside the script; one aggregator exclusively records admissions in checks.md. Only the root owns progress.md, which is not updated during an active Workflow. The root must not modify this run's files or re-execute its nodes while it runs. A changed graph requires a newly approved revision.
Mode B needs separate approval. After reviewing graph.md, the user explicitly approves the phase, number of agents, concurrency, write permissions and budget. Invoking /graph-task or a tool permission prompt is not a substitute. For long or risky tasks, use multiple smaller Workflows with verification between phases; a running script cannot request arbitrary mid-run sign-off.

Resuming the original session

Return to the same Claude Code session (using claude --resume where needed) and use native Workflow relaunch. Changes to prompts, call order or failures may rerun completed agents: also recheck inputs and evaluators; verify remote state before repeating an external write. With context intact the agent rereads protocol §13–14 and first checks the workflow.js and graph.md hashes: if either changed, it is a new run.

Continuing in a new session

Reread the full normative protocol, then graph.md, progress.md and checks.md. Verify saved artifact hashes, record revoked admissions in checks.md and approve a new Workflow only for remaining nodes. This is a new run, not a restoration of the old runtime.

Official reference: Claude Dynamic Workflows. The execution mechanism does not override scope restrictions, approval rules, or verification requirements. On Pro, Dynamic Workflows must be enabled in /config.

04 / Guarantees

What “verified” really means

A model cannot accept its own work on trust. It must show exactly which saved artifact was checked, by which evaluator, and with what result.

GATE

Bind evidence to a specific version

A PASS records verifiable input, output, contract and evaluator versions; without them the result is UNVERIFIED. When a version changes, the revocation of the old PASS and its dependents is recorded in checks.md and holds until rechecked.

DETERMINISTIC FIRST

Deterministic checks before opinions

Sorting, comparisons, counting, and tests belong in tools and code. Use a model for ambiguous judgment and root-cause analysis, not tasks with one deterministic answer.

REVIEW

Risk-proportionate review

By default, use a producer and deterministic checks. Add independent review when the risk justifies the cost. A judge is needed for blocking disagreements, not after every pair of opinions.

FILE OWNERSHIP

One owner for each state file

During a Workflow, gate agents save separate evidence and one aggregator updates checks.md. Only the root updates progress.md between phases. See section 02 for recovery scenarios.

CategoryExampleGate behavior
HIGHSeriously incorrect output, failure in normal use, or critical security defectFAIL — blocks downstream consumption
MEDIUMWrong behavior in a realistic edge caseFAIL — requires a fix or authorized contract revision
LOWNonessential style, wording, or minor cosmetic effectsReport only; no automatic correction loop
CHECKS: failed / unknownRequired test failed, was not run, or has unverified evidenceFAIL or UNRESOLVED — never PASS
Never weaken valid tests to fit the result. If the contract or test harness is wrong, route the issue to its owner. Do not count it against the producer. If a test requires something the contract neither states nor implies, it is a spec gap: ask the contract owner; no correction attempt is charged. A contract change invalidates affected downstream admissions.
05 / Resources

Budget the entire execution tree, not one agent

Measure the full cost of an accepted result: orchestrator, workers, reviewers, retries, external tools, and closure.

06 / Setup

Using the skill in one project

Unpack into the project root. The package does not change user-level instructions, global settings, or files in other projects.

Extract into the target project root

The paths should look like this: .claude/skills/graph-task/SKILL.md, .claude/skills/graph-task/references/protocol.md and .claude/skills/graph-task/docs/guide.ru.html. Do not nest .claude inside another .claude. The English edition is available alongside the Russian edition at .claude/skills/graph-task/docs/guide.en.html.

Open Claude Code from this project

Invoking /graph-task loads the skill. The agent does not invoke it on its own because the setting disable-model-invocation: true.

Describe the task, acceptance criteria, and scope

If budgets or limits are missing, the agent must not invent authorization. It reuses existing permissions and asks only about gaps that materially affect safe execution.

Review the graph and approve execution first

The plan is saved to .agent-runs/<task-id>/graph.md. For mode B, separately approve its phase, agent cap, concurrency and budget after reviewing the graph. Then run the trial before any fan-out, execute nodes, apply gates and report results.

/graph-task Fix the regression in the authentication module. OUTPUT: corrected code in this project. CHECKS: authentication tests pass; no session regressions. SOURCES: existing repository code, tests, and logs. SCOPE: auth module and its tests only. LIMIT: up to 2 hours or 12 nodes. BUDGET: use available counters; do not claim a hard cap without a watchdog. REVIEW_POLICY: independent review for security-sensitive changes. Propose mode A/B, write the graph and request approval. If B, separately ask permission for its phase, agent count, and concurrency.

Where each task run stores its artifacts

.agent-runs/ └── auth-regression-001/ ├── graph.md ← nodes, edges, criteria ├── checks.md ← passing/failing gates ├── progress.md ← checkpoints and next steps └── evidence/ ← evidence artifacts and index

The run ID is illustrative. The exact evidence/index layout depends on the task. A separate folder prevents one run from overwriting another run’s reports. For mode B, the script is saved as workflow.js and its path and hash are recorded in progress.md before launch; the root adds the run ID after regaining control, and unavailable details remain unknown/pending.

When to use it

Cross-module refactors, data migrations, risky integrations, broad-source research, and long tasks that may span multiple sessions.

When not to use it

One-off answers, a trivial edit, or a single-file inspection. Plain Claude Code with tests is often enough. Even when the skill is invoked, a single simple node without external side effects takes the lightweight path: a short baseline, a bounded change, the mandatory gate and a brief record in checks.md and progress.md, without extra agents or independent review.

07 / Optional capability

Configure Advisor separately

This archive does not install Advisor. It may help with architectural uncertainty, but it should not silently multiply the cost of parallel work.

ScenarioRecommendationReason
Routine implementationNo AdvisorAvoid extra context reads; tests suffice
Difficult architectural decisionAdvisor for the decision stageSecond opinion before a high-stakes choice
Two repeated failures with unclear causeAdvisor if the model pairing is supportedChallenge the causal hypothesis instead of retrying blindly
Large parallel fan-outDo not enable Advisor across the entire run without checking inheritanceDo not assume an undocumented per-worker Advisor disablement
Final code acceptanceTests/gates + risk-based reviewAdvisor opinions are not correctness evidence

For a one-session experiment, use the CLI flag, if the selected model pair and provider support Advisor:

cd /path/to/project claude --model sonnet --advisor opus

Or enable it inside Claude Code with /advisor opus, but be aware that this choice is usually persisted to user settings and may affect other projects. The --advisor flag applies only to this session. The skill works just as well without Advisor.

Verify availability: Advisor is an experimental feature subject to provider and model-pair restrictions. Supported models, versions, plans, and behavior may change. Consult the official Advisor documentation.
08 / FAQ

Short answers

Must the agent read this HTML on every run?

No. It must read the normative references/protocol.md, while this visual guide is for people only. The SKILL.md states this boundary explicitly.

Does a project-local skill need a global CLAUDE.md?

No. The skill lives in project/.claude/skills/graph-task/. It must not change global files. Existing project instructions are preserved; AGENTS.md may be updated only with authorization.

Will Claude automatically create many subagents?

No. A small task may use one node and direct tools. Native Dynamic Workflow is useful only when complexity or parallelism justifies a separate orchestration script.

Can a prompt guarantee a spending cap?

No. You need a real counter or watchdog that can stop new spending. Without that, the estimate must not be described as a hard limit.

Which files matter when starting a new session?

See section 02 — Execution modes: read the normative protocol, then verify the intended run’s graph.md, progress.md, checks.md and accepted artifact hashes before resuming the remaining nodes.
