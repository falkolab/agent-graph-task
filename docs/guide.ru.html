01 / Архитектура

Кто за что отвечает

Skill задаёт порядок работы. Протокол определяет неизменяемые критерии качества. Механизм исполнения подбирается под задачу. Советник не является частью Skill.

ИНСТРУКЦИЯ

Skill /graph-task

Принимает задачу, связывает контракт, инициирует граф и соблюдает этапы проверки. Загружается только при ручном вызове.

ПОЛИТИКА

protocol.md

Детальные правила: baseline, права, версии артефактов, проверки, ревью, лимиты, расходы, остановка и восстановление.

Инструменты / Workflow

Прямые команды, одиночные субагенты или нативные Dynamic Workflows. Не автоматическое распараллеливание любой задачи.

02 / Два способа исполнения

Один согласованный граф — два возможных исполнительных режима

Это не две конкурирующие системы. graph.md описывает, что должно быть сделано и как проверяется результат. Claude выбирает, как исполнять этот план. При использовании Dynamic Workflow возникает второе, исполняемое представление графа — JavaScript.

От спецификации к исполнению и проверенным артефактам

РЕЖИМ A

Без Dynamic Workflow

Claude выполняет узлы напрямую и при необходимости делегирует ограниченные исследования и проверки субагентам. Тот же graph.md, те же ограничения прав, доказательства, gates и документы завершения.

Лучше для небольшого либо неоднородного графа, где отдельный JavaScript-оркестратор не окупится.

РЕЖИМ B

С Dynamic Workflow

Claude формирует JavaScript-граф, сам скрипт задаёт зависимости и порядок вызовов, а runtime запускает агентов и хранит промежуточные результаты. graph.md остаётся утверждённой спецификацией, а не вторым диспетчером активных узлов.

Лучше для множества похожих, независимых задач, когда оркестрация скриптом снижает нагрузку на контекст.

Синхронизация и ответственность: каждый Workflow привязан к конкретной ревизии/хешу graph.md и ограниченному набору узлов. До запуска в progress.md фиксируются фаза, хеш графа и разрешения; там же до запуска фиксируются путь и хеш сохранённого workflow.js, который запускается через scriptPath; фактический ID запуска корень дописывает после возврата управления, если он доступен. Внутри скрипта отдельные проверяющие агенты выполняют gates, затем единственный агрегатор фиксирует допуски в checks.md. progress.md принадлежит только корню, но не обновляется во время активного Workflow. Пока запуск активен, корень не меняет файлы этой фазы и не запускает те же узлы повторно. При изменении графа нужна новая согласованная ревизия.
Режим B требует отдельного согласия. После просмотра graph.md пользователь отдельно подтверждает фазу, число агентов, параллелизм, права записи и бюджет. Вызов /graph-task и обычное окно разрешения инструмента не заменяют этого решения. Для больших или рискованных задач безопаснее несколько небольших Workflow с проверками между фазами; внутри одного Workflow нельзя запросить произвольное согласование пользователя.

Возобновление исходной сессии

Сначала вернитесь в ту же сессию Claude Code (при необходимости claude --resume) и используйте штатное возобновление Workflow. При изменении промпта, порядка вызовов или после ошибок даже завершённые агенты могут запуститься снова: после повторного запуска сверяйте также входы и проверки; внешнюю запись не повторяйте, пока не подтверждён её результат. При сохранённом контексте агент перечитывает §§13–14 протокола и сначала сверяет хеши workflow.js и graph.md: если один из них изменился, это уже новый запуск.

Продолжение в новой сессии

Прочитайте нормативный протокол полностью, затем graph.md, progress.md и checks.md. Сверьте хеши допущенных артефактов, запишите отзыв устаревших допусков в checks.md и согласуйте запуск только оставшихся узлов. Это новый Workflow, а не восстановление его прежнего runtime.

Официальный справочник: Claude Dynamic Workflows. Способ исполнения не отменяет пользовательские ограничения, план согласования или требования к проверке. На тарифе Pro Dynamic Workflows включаются через /config.

04 / Гарантии

Что значит «проверено»

Модель не принимает собственную работу на веру. Она должна показать, какой именно сохранённый артефакт проверен, чем и с каким результатом.

GATE

Привязка к конкретной версии

PASS фиксирует проверяемые версии значимых входов, результата, контракта и проверяющего; без них результат — UNVERIFIED. Если версии изменились, отзыв прежнего PASS и зависимых допусков записывается в checks.md и действует до повторной проверки.

DETERMINISTIC FIRST

Код раньше экспертного мнения

Сортировка, сравнение, подсчёт и тесты выполняются инструментами. Модель используется для неоднозначного суждения и поиска причин, а не для операций с единственным правильным ответом.

REVIEW

Ревью соразмерно риску

По умолчанию — исполнитель и детерминированный тест. Независимое ревью добавляется только когда риск оправдывает цену. Judge нужен при блокирующих противоречиях, а не после каждой пары мнений.

FILE OWNERSHIP

Разделение владельцев состояния

Во время Workflow проверяющие сохраняют отдельные доказательства; один агрегатор обновляет checks.md. Только корневой агент обновляет progress.md между фазами. Подробности восстановления — в разделе 02.

MEDIUMОшибка поведения на реалистичном пограничном случаеFAIL — требует исправления или разрешённой смены контракта

Нельзя «подогнать тесты» под результат. При ошибке контракта или тестового стенда проблема возвращается владельцу спецификации/проверки. Такая ошибка не считается неудачной попыткой исполнителя. Если тест требует того, чего нет в контракте и что из него не следует, это пробел спецификации: вопрос владельцу контракта, попытка исполнителя не расходуется. Меняется контракт — пересматриваются затронутые downstream-допуски.

Контроль расходов — всего дерева, не одного агента

Измерять нужно полную стоимость успешного решения: оркестратор, исполнители, ревьюеры, повторы, внешние инструменты и завершение процесса.

Что входит в общий бюджет

Диаграмму можно прокручивать горизонтально →

Промпт не умеет физически остановить расходы. Если обещается жёсткий бюджет, нужен реальный счётчик и внешний механизм остановки. Без него лимит — только инструкция и оценка. Нельзя превращать стоимость API в «процент подписки» без отдельного наблюдаемого счётчика.
06 / Запуск

Как использовать в одном проекте

Пакет располагается в корневой папке репозитория; он не изменяет пользовательские инструкции, глобальные настройки или файлы другого проекта.

Распакуйте в корень нужного проекта

Пути должны получиться именно такими: .claude/skills/graph-task/SKILL.md, .claude/skills/graph-task/references/protocol.md и .claude/skills/graph-task/docs/guide.ru.html. Не размещайте .claude внутри другой .claude. Английское руководство лежит рядом в .claude/skills/graph-task/docs/guide.en.html.

Откройте Claude Code в этом проекте

Вызов /graph-task добавит инструкцию. Skill не вызывается агентом самовольно: установлен параметр disable-model-invocation: true.

Опишите задачу, критерии приёмки и границы

Если бюджет и ограничения не определены, агент не должен изобретать «разрешение на расход». Он использует существующие разрешения и уточняет только существенные пробелы.

Сначала оцените граф и одобрите исполнение

Граф сохраняется в .agent-runs/<task-id>/graph.md. Для режима B отдельно согласуйте фазу, максимальное число агентов, параллелизм и бюджет после предъявления графа. Далее — пробный прогон перед любым fan-out, исполнение, gates и отчёт.

/graph-task Исправь регрессию в модуле авторизации. OUTPUT: исправленный код в текущем проекте. CHECKS: тесты авторизации проходят; нет регрессий по сессиям. SOURCES: существующий код, тесты и логи в репозитории. SCOPE: только модуль auth и его тесты. LIMIT: до 2 часов или 12 узлов. BUDGET: используй доступные счетчики; не утверждай hard cap без watchdog. REVIEW_POLICY: отдельная проверка при изменении безопасности. Сначала предложи режим A/B, запиши граф и запроси согласование. Если B — отдельно запроси разрешение на конкретную фазу, число агентов и параллелизм.

Где лежат результаты конкретного запуска

.agent-runs/ └── auth-regression-001/ ├── graph.md ← узлы, рёбра и критерии ├── checks.md ← пройденные/непройденные gates ├── progress.md ← состояние и следующий шаг └── evidence/ ← проверяемые файлы и индекс

Идентификатор запуска — пример. Конкретная структура индекса/материалов определяется задачей. Выделенная папка исключает перезапись отчётов соседних запусков. Для режима B скрипт сохраняется как workflow.js, его путь и хеш записываются в progress.md до запуска; run ID корневой агент дописывает после возврата управления, неизвестное остаётся unknown/pending.

Когда использовать

Рефакторинг нескольких подсистем, миграция данных, интеграция с рисками, исследование с большим числом источников, сложные задачи, которые потребуется продолжать между сессиями.

Когда не нужно

Разовый ответ, простая правка, проверка одного файла. Обычного Claude Code с тестами часто достаточно. Даже при вызове Skill один простой узел без внешних эффектов идёт облегчённым путём: короткий baseline, ограниченная правка, обязательный gate и краткая запись в checks.md и progress.md, без дополнительных агентов и независимого ревью.

07 / Необязательная надстройка

Advisor включается отдельно

Советник не устанавливается этим архивом. Он может быть полезен при архитектурной неопределённости, но не должен незаметно умножать стоимость параллельной работы.

СценарийЧто рекомендованоПочему
Рутинная реализацияБез AdvisorМеньше дополнительных чтений контекста; хватает тестов
Сложное архитектурное решениеAdvisor на ограниченный этапВторое мнение до рискованного выбора
Две повторные неудачи с неясной причинойAdvisor при совместимости моделейПроверить причинную гипотезу, не продлевая слепые повторы
Массовый fan-outНе включать Advisor на весь запуск без анализа наследованияНе полагаться на неподтверждённое отключение у отдельных workers
Приёмка готового кодаTests/gates + риск-ревьюМнение Advisor не является доказательством корректности

Для разового эксперимента запустите новую сессию с флагом, если выбранная пара моделей и ваш провайдер поддерживают Advisor:

cd /path/to/project claude --model sonnet --advisor opus

Или включите его внутри Claude Code командой /advisor opus, но учтите: выбор через команду обычно сохраняется в пользовательском конфиге и может затронуть другие проекты. Флаг --advisor действует только для запущенной сессии. Вся работа Skill может выполняться и без Advisor.

Проверяйте фактическую доступность: Advisor — экспериментальная функция с ограничениями по провайдеру и совместимости моделей. Конкретные модели, версии, тарифы и поведение могут измениться. См. официальную документацию Advisor.
08 / Частые вопросы

Короткие ответы

Агент обязан читать этот HTML при каждом запуске?

Нет. Агенту нужно читать нормативный references/protocol.md; HTML предназначен только для человека и для применения Skill не требуется.

Для одного проекта нужен глобальный CLAUDE.md?

Нет. Skill находится внутри project/.claude/skills/graph-task/. Он не должен менять глобальные файлы. Существующие проектные инструкции сохраняются; AGENTS.md может обновляться только с разрешением.

Будет ли Claude автоматически создавать много субагентов?

Нет. Для маленькой задачи допустим один узел и инструменты. Нативный Dynamic Workflow нужен только там, где сложность/параллельность оправдывает отдельный скрипт оркестрации.

Можно ли гарантировать ограничение стоимости одним промптом?

Нет. Необходим внешний счётчик или watchdog с реальной возможностью остановить новые расходы. Если этого нет, оценка не называется жёстким лимитом.

Какие файлы переносить в новую сессию?

См. раздел 02 «Два режима»: при новой сессии повторно прочитайте протокол, проверьте graph.md, progress.md и checks.md, затем подтвердите запуск оставшихся узлов.
